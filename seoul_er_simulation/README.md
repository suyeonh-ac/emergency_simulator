> 심장 병상을 쓴다" 같은 로직을 원하면 requiredSpecialty와는 별개인 ICU 자원 키를

## 실행 방법

`index.html`을 더블클릭해서 브라우저로 열면 됩니다. 로컬 서버 없이 바로 동작합니다
(데이터를 `fetch`가 아니라 `<script src="...">`로 불러오는 방식이라 `file://`로 열어도
CORS 문제가 없습니다). 지도 타일(Esri 다크 캔버스)·Leaflet 라이브러리·폰트는 여는 시점에
인터넷에서 불러오므로, 발표 장소에서 한 번 미리 열어 확인해두는 걸 권장합니다. 그 외에는
(환자 배정, 경로 재생 등) 외부 API를 전혀 호출하지 않습니다 — 이동 경로는 전부 사전
계산해서 캐시에 구워둔 값을 재생만 하는 것이고, 시연 중에 카카오/OSRM 서버를 다시
호출하지 않습니다.

## 데이터 중 실측 vs 가정(합성) 구분 — 팀 리뷰 시 가장 먼저 볼 부분

**실측 데이터**
- 병원의 이름·위치(위경도)·등급(권역/지역센터/지역기관/신고기관): `data/ems_facilities_all.csv`
  (사용자가 준 공공데이터 기반 원본을 서울로 필터링, 원본은 74곳). **2026-09-20부터
  `hospitals.json`에는 이 중 응급똑똑 세부 병상데이터가 있는 51곳만 남아 있습니다** —
  아래 "51곳으로 범위 축소" 섹션 참고.
- 이동 경로의 도로 형태·거리·소요시간(4×4 격자 16지점 × 병원 51곳 = 816개 구간, 원래는
  74곳 기준 1,184개 전 구간이었다가 51곳으로 필터링됨):
  **카카오모빌리티 길찾기(Directions) API** (`priority=RECOMMEND`)에서 실제 도로망 +
  실시간 교통 상황을 반영해 계산한 값 (`data/route_results.json`). 이전 버전은 OSRM
  (교통 미반영)을 썼는데, 그 결과는 `data/route_results_osrm.json`에 비교용으로
  남겨뒀습니다(74곳 기준, 필터링 전).
- 병원별 병상수(`capacity`)와 보유 진료과(`specialties`): **국립중앙의료원 응급의료정보

## 병상수·진료과 실측 반영 (2026-09-17, 3차)

**왜 바꿨나**: 지난 버전까지 병상수·진료과는 `random.seed(42)` 합성값이었습니다.
사용자 피드백 두 가지를 반영해 국립중앙의료원 응급의료정보 Open API의 **실측 자료**로
교체했습니다.

1. *"시뮬레이션이니까 현재 가용병상수 보다는 최대 병상수가 중요하지. 어차피 가상으로
   환자 생성해서 배정하는걸 볼거니까."* — E-Gen API는 두 종류의 병상 필드를 줍니다.
   `getEmrrmRltmUsefulSckbdInfoInqire`(응급실 실시간 가용병상정보 조회)의 `hvec` 등은
   "지금 이 순간 남은 병상"(마이너스도 나올 수 있음, 실시간으로 계속 바뀜)이고,
   `getEgytBassInfoInqire`(응급의료기관 기본정보 조회)의 `hperyn`은 "응급실 기준(허가)
   병상수" — 즉 이 응급실이 원래 몇 병상 규모로 운영되는지를 나타내는 값입니다.
   시뮬레이션은 환자를 가상으로 계속 생성해서 배정하므로, "지금 몇 자리 남았나"가 아니라
   "이 응급실의 최대 수용력이 몇 명인가"가 맞는 값이라 `hperyn`을 `capacity`로 썼습니다.
2. *"응급실 별로 진료과목을 확정짓는거야."* — 이전에는 CT/MRI/인공호흡기 등 장비
   보유 Y/N 플래그로 진료과를 간접 추론했습니다. 이제는 같은 API의 `dgidIdName` 필드
   (병원이 실제로 신고한 운영 진료과목 전체 텍스트, 예: "내과,외과,신경외과,...")를 직접
   파싱해서 확정합니다. 시뮬레이션이 쓰는 4개 카테고리에 대한 매핑 규칙:
   - `일반`: 항상 포함 (모든 응급실의 기본 수용 능력으로 간주)
   - `외상`: 진료과 목록에 "외과" 또는 "신경외과" 또는 "정형외과"가 있으면
   - `심장`: "흉부외과"(심장혈관흉부외과 포함) 또는 "심장"이 있으면
   - `소아`: "소아청소년과"가 있으면
   → 매핑 코드: `scripts/1c_apply_egen_data.py`의 `classify_specialties()`.

**결과가 어떻게 달라졌나**: 병상수 분포가 등급별 임의 범위(2~14, 평균 약 7)에서 실제
분포로 넓어졌고, 진료과 커버리지도 더는 등급별 고정 세트가 아니라 병원마다 다르게
나옵니다 — 이전에 지적했던 "환자 배정 진료과가 균등 25%라 비현실적" 문제도 병원 쪽
커버리지가 실측으로 바뀌면서 부분적으로 개선됨. 단, 환자가 필요로 하는 진료과 자체는
아직 `sim.js`에서 4개 중 균등 난수로 뽑고 있어 그 쪽은 여전히 개선 여지가 있습니다.
(수치는 74곳 전체 기준 당시 값이었고, **2026-09-20부터 51곳으로 범위가 줄어든 최종
기준으로는** 병상수 8~73 · 평균 25.5, 진료과 커버리지는 51곳 중 외상 51 · 심장 38 ·
소아 44 · 일반 51 — 아래 "51곳으로 범위 축소" 섹션 참고.)

**미보고 병원 처리(fallback)**: 74곳 중 16곳은 `hperyn`을 아직 API에 보고하지 않아
(주로 소규모 병원) 비율 추정치를 썼습니다. `hperyn`이 있는 58곳 표본에서
`hperyn ÷ dutyHano`(병원 전체 병상수 대비 응급실 병상 비율)의 중앙값(약 4.3%)을 구해,
해당 병원의 `dutyHano`에 곱한 값을 추정치로 씁니다(최소 2병상). 콘솔에 어떤 병원이
fallback을 썼는지 다 출력되고, `hospitals.json`의 각 항목에는 `_egenSource` 필드로
`"hperyn(실측)"`인지 `"fallback(...)"`인지 표시해뒀습니다. (참고로 이 `capacity` 값은
51곳에 대해서는 어차피 아래 "중환자실·수술실 자원 반영"에서 응급똑똑 실측치로 다시
교체되므로, fallback 여부가 최종 결과에 영향을 주는 건 51곳 밖 병원들뿐이었는데 —
그 병원들은 2026-09-20부터 `hospitals.json`에서 아예 제외됐습니다. 남은 51곳 중에서도
`_egenSource`가 fallback인 병원이 3곳 있지만, 이 병원들도 `capacity`는 이미 응급똑똑
실측치로 교체되어 있어 fallback 값 자체는 최종 결과에 쓰이지 않습니다.)

**한 가지 데이터 품질 이슈(참고, 해결됨)**: 74곳 중 `A1107402`(서울대학교치과병원)는
진료과 목록에 응급의학과가 없고 치과 계열 과만 있는 이슈가 있었습니다 — 이 병원은
응급실운영신고기관이라 응급똑똑 세부 데이터가 없었고, 2026-09-20에 23곳을 제외할 때
같이 빠져서 최종 51곳에는 포함되지 않습니다.

## 중환자실·수술실 자원 반영 (2026-09-19, 4차)

**왜 바꿨나**: 지난 버전까지 배정 로직은 "응급실 병상 + 진료과 일치"만 봤습니다. 사용자가
응급똑똑 앱을 캡쳐해서 "이 데이터를 쓰는게 어떠냐"고 제안했고, 확인해보니 공개
API/웹사이트로는 응급똑똑 앱이 보여주는 병상 "전체(최대 수용치)"가 아니라 "지금 당장
가용한" 숫자만 조회할 수 있었습니다(분모가 아니라 분자만 공개됨). 그래서 사용자가 직접
응급똑똑 앱에서 51곳의 실제 "전체" 수치를 하나씩 확인해 엑셀로 정리해줬고, 이를 반영해
(1) `capacity`를 더 세부적인 실측치로 교체하고, (2) 시뮬레이션에 **중환자실·수술실을
새로운 배정 제약 자원으로 추가**했습니다 — 환자가 중증/수술이 필요하면 응급실 병상뿐
아니라 그 병원의 ICU/수술실 여유도 있어야 배정에 성공합니다.

**응급실 병상수(`capacity`) 재교체**: 51곳은 응급똑똑의 "응급실병상(최대)" 그룹 8개
세부항목(일반/소아/외상소생실/일반격리/음압격리/소아일반격리/소아음압격리/코호트격리)
합계로 `capacity`를 교체했습니다(1c 단계의 `hperyn` 기반 값보다 더 세부적이고 최근
실측이라 우선). 나머지 23곳(응급실운영신고기관)은 응급똑똑에 세부 데이터가 없는 소규모
병원이 많아 이번 수집 대상에서 제외되었고, `hperyn`/추정치 값을 그대로 유지합니다.

**중환자실·수술실(`resources`) — `sim.js`의 진료과 4분류(외상/심장/소아/일반)에 맞춘
매핑**: 공식 분류가 아니라 이번 시뮬레이션을 위한 모델링 가정입니다 — 팀에서 가중치를
조정하고 싶으면 `scripts/1e_apply_manual_bed_detail.py`의 `icu_buckets()`/`surgery_total()`만
고치면 됩니다.

```
icu.외상 = 중환자실.외과 + 중환자실.신경외과 + 중환자실.화상 + 외상전용병상.중환자실
icu.심장 = 중환자실.심장내과 + 중환자실.흉부외과
icu.소아 = 중환자실.소아 + 중환자실.신생아 + 응급전용병상.소아중환자실
icu.일반 = 중환자실.일반 + 중환자실.내과 + 중환자실.신경과 + 중환자실.음압격리
surgery  = 기타병상.수술실 + 외상전용병상.수술실   (진료과 구분 없이 병원 전체 풀로 취급)
```

(2026-09-21부터: 화상/신생아/음압격리 3개 항목이 위 공식에 포함됩니다 — 처음 이 공식을
만들 때는 8개 항목만 다뤘고 나머지 3개는 계산에서 빠져 있었습니다. 자세한 내용은 위
"6차 업데이트" 참고.)

51곳 밖의 23곳은 `resources` 전부 0 — "이 병원엔 ICU/수술실이 없다"는 뜻이 아니라
"이번에 확인하지 못했다"는 뜻입니다. 반영 결과: 45개 병원의 `capacity`가 응급똑똑 실측
합계로 교체됐고, ICU 자료를 근거로 `specialties`가 보정된 병원이 2곳 있습니다
(A1100054 성애병원 +심장, A1122033 기쁨병원 +심장 — ICU에 해당 과 병상이 있는데
진료과 목록엔 빠져 있던 경우에 대한 안전장치). 2026-09-21 수정 이후에는 신생아 ICU가
새로 반영되면서 A1100026 구로성심병원·A1100045 씨엠병원 2곳에 +소아가 추가로
보정됐습니다.

**배정 로직에 어떻게 반영했나**: 환자 생성 시 고정 확률로 `needsICU`(22%)·`needsSurgery`
(12%)를 부여합니다(`sim.js`의 `ICU_NEED_PROB`/`SURGERY_NEED_PROB`). 이 확률은 실제
중증도 분포를 조사한 값이 아니라 **당장은 단순화를 위한 자리표시 상수**입니다 — 나중에
포아송+KTAS 작업을 하게 되면 이 확률을 중증도 기반 계산으로 교체하면 됩니다. 배정 시
응급실 병상 + 진료과 일치에 더해, `needsICU`면 그 병원의 해당 진료과 ICU 버킷에 여유가
있어야 하고 `needsSurgery`면 수술실(병원 전체 풀)에 여유가 있어야 배정에 성공합니다.
병원 목록·지도 팝업에 `ICU 점유/전체 · 수술실 점유/전체`가 새로 표시됩니다.

**참고 — 교수님 방향과의 긴장 관계**: 5주 계획의 다른 항목("환자 생명주기를 배정
시점까지로 단순화하고, 배정 이후 치료 진행/완료 추적은 제거")은 환자 쪽 추적을 줄이는
방향인데, 이번 작업은 반대로 병원 쪽에 점유 추적 차원(ICU 4버킷 + 수술실)을 하나 더
늘렸습니다. 두 방향이 정면으로 충돌하는 건 아니지만(생명주기 단순화는 "환자가 배정
후 어떻게 되는지"를, 이번 건은 "배정 가능 여부를 무엇으로 판단하는지"를 다룸), 다음
미팅에서 팀/교수님과 한 번 짚고 넘어가는 게 좋습니다.

## 51곳으로 범위 축소 (2026-09-20, 5차)

**왜 바꿨나**: 사용자 요청 — "74개 말고 직전에 올려준 엑셀에 있는 51개로 하자". 74곳 중
23곳(응급실운영신고기관)은 응급똑똑 세부 데이터가 없어 `resources`(중환자실·수술실)가
항상 0이었고, 이 병원들은 중증/수술이 필요한 환자를 원천적으로 받을 수 없는 채로
시뮬레이션에 섞여 있었습니다. 사용자가 직접 실측해준 51곳(법정 응급의료기관: 권역응급의료
센터 7 + 지역응급의료센터 24 + 지역응급의료기관 20)만 남기면, 병원 전부가 `capacity`·
`specialties`·`resources` 모두 실측 데이터라는 뜻이라 `scripts/1f_filter_manual_hospitals.py`
로 나머지 23곳을 제외했습니다.

**이동 경로 캐시는 다시 안 받았습니다**: `data/route_results.json`은 4×4 격자 16개
지점 × (당시) 병원 74곳 전체 = 1,184구간을 전부 사전 계산해둔 것이었어서, 51곳으로
줄여도 필요한 조합(16 × 51 = 816구간)은 이미 다 들어 있었습니다. 그래서 카카오 API를
다시 호출하지 않고, 기존 결과에서 남기는 51곳에 해당하는 구간만 골라 병원 인덱스를
새로 매겼습니다(0~73 → 0~50). 발생 지점(4×4 격자 좌표 자체)은 그대로 뒀습니다 — 이미
실도로 경로가 있는 지점들이라 좌표를 바꾸면 오히려 캐시가 깨지기 때문입니다.

**결과**: `hospitals.json`이 74곳에서 51곳으로 줄었고, 제외된 23곳은 전부 등급이
"응급실운영신고기관"입니다(권역/지역센터·지역기관은 전부 유지). 화면상 병원 수·타이틀·
경로 구간 수(1,184→816) 표기도 전부 갱신했습니다. `resources`가 0인 병원이 더는 없어서,
"확인 못함" 케이스에 대한 예외 처리(README 위쪽의 "응급똑똑에 세부 데이터가 없어
resources가 0" 설명)는 이제 해당하는 병원이 없습니다 — 코드에는 안전장치로만 남아 있습니다.

**참고**: `data/ems_facilities_all.csv`, `data/egen_raw.json`, `data/route_results_osrm.json`
등 74곳 시절 원본 파일들은 그대로 남겨뒀습니다(재현·비교용). `data/manual_bed_detail.xlsx`,
`data/bed_detail_raw.json`도 원래부터 51곳 기준이라 이번에 손댈 게 없었습니다.

## 이동 경로 캐시 관련 트레이드오프 (+ "점선이 너무 자주 나옴" 문제 수정)

**처음 버전(2026-09-17 오전)의 문제**: 서울을 4x4 격자(16개 대표 지점)로 나누고, 각
지점에서 직선거리 기준 가장 가까운 병원 "8곳"만 후보로 좁혀서 사전 계산했습니다(총 128개
구간). 그런데 실제 배정 로직은 거리만 보는 게 아니라 병상 여유·진료과 일치까지 봅니다.
서울 74개 병원 중 모든 진료과(외상·심장·소아·일반)를 다 보는 권역응급의료센터는 7곳뿐이라,
어떤 격자 지점에서는 가장 가까운 8곳 안에 권역센터가 하나도 없는 경우가 있었습니다. 그
근처 병원들이 만실이 되면 배정이 권역센터 등 "8곳 밖"으로 튀는데, 그 구간은 캐시에 없어서
직선 근사(점선)로 그려졌던 것 — 실제로 데모를 돌려보면 점선이 너무 자주 나오는 것으로
나타났습니다.

**수정(2026-09-17 오후)**: 후보 수 K를 8에서 **병원 전체(74)로 늘려서, 16개 발생지점 ×
74개 병원의 모든 조합(1,184구간)을 다 사전 계산**했습니다. 이제 어떤 지점에서 어떤
병원으로 배정되어도 항상 캐시에 실도로 경로가 있습니다. 직선 근사(점선)는 이론상 더는
나오지 않고, 코드에는 만약을 위한 안전장치로만 남아 있습니다.

격자를 더 촘촘하게(예: 6x6) 만들고 싶으면 `scripts/2_generate_route_plan.py`의 `GRID`
값을 바꾸고 2~4단계를 다시 실행하면 됩니다(`K`는 `len(hospitals)`로 이미 "전체"를
가리키고 있어서 손댈 필요 없음). 3단계는 인터넷이 되는 브라우저에서 다시 돌려야 함 —
카카오 API 호출이 필요해서 이 저장소 안의 정적 스크립트만으로는 재실행되지 않습니다.

**카카오모빌리티 API 호출 비용 주의**: 4x4×74=1,184회 호출은 무료 할당량(월 요청 한도)
안에서 충분하지만, 격자를 더 촘촘하게 하면 호출 수가 배로 늘어납니다(예: 6x6이면
36×74=2,664회). 카카오 디벨로퍼스 콘솔에서 호출 한도/과금 정책을 미리 확인하세요.

## 재현 순서 (데이터를 처음부터 다시 만들 경우)

1. `python scripts/1_generate_hospitals.py`
1-1. (병상수·진료과 실측 반영) data.go.kr에서 **일반 인증키(Encoding)**를 발급받아
   `scripts/1b_fetch_egen_capacity.js`의 `SERVICE_KEY`에 채운 뒤, 인터넷이 되는 브라우저
   콘솔에서 그 파일 전체를 실행합니다. 완료되면 `window.__EGEN_RESULTS__`를
   `JSON.stringify`해서 `data/egen_raw.json`으로 저장하고, `python
   scripts/1c_apply_egen_data.py`를 실행해 `hospitals.json`/`hospitals.data.js`에
   반영합니다. (이 단계를 건너뛰면 1단계의 등급별 합성값이 그대로 남습니다.)
1-2. (중환자실·수술실 자원 반영, API 불필요) `data/manual_bed_detail.xlsx`는 이미 이
   저장소에 있으므로 바로 `python scripts/1d_extract_manual_bed_detail.py`를 실행해
   `data/bed_detail_raw.json`을 만들고, 이어서 `python scripts/1e_apply_manual_bed_detail.py`
   를 실행해 `hospitals.json`/`hospitals.data.js`에 반영합니다.
2. `python scripts/2_generate_route_plan.py`
3. 카카오 디벨로퍼스에서 앱을 만들고 **REST API 키**를 발급받은 뒤 (플랫폼 키 중
   REST API 키가 필요합니다 — JavaScript 키/네이티브 앱 키/어드민 키는 불필요), 해당 앱에
   "카카오모빌리티" 제품이 활성화돼 있는지 확인합니다. `data/route_plan.json`의 내용을
   `scripts/3_fetch_routes.js`의 `PLAN` 상수에 붙여넣고, `KAKAO_REST_API_KEY`에 본인의
   REST API 키를 채운 뒤, 인터넷이 되는 브라우저 콘솔에서 그 파일 전체를 실행합니다.
   총 1,184개 구간을 동시요청 8개로 처리해서 40~90초 정도 걸립니다 — 콘솔에 결과 객체
   (`{done:true, total:1184, ...}`)가 뜰 때까지 기다리세요.
4. 콘솔에 나온 `window.__ROUTE_RESULTS_KAKAO__`를 `JSON.stringify`해서
   `data/route_results.json`으로 저장
5. `python scripts/4_build_route_cache.py`
6. (51곳으로 범위 축소) `python scripts/1f_filter_manual_hospitals.py` — 응급똑똑 세부
   데이터가 없는 23곳을 `hospitals.json`에서 제외하고, `route_results.json`/
   `route_cache.data.js`/`route_plan.json`을 51곳 기준으로 필터·재매핑합니다(API
   재호출 없음). **이 단계를 건너뛰면 74곳 전체가 그대로 남습니다.**

(OSRM 버전을 다시 만들고 싶다면 3~5단계를 `scripts/3_fetch_routes_osrm.js`,
`data/route_results_osrm.json`, `scripts/4_build_route_cache_osrm.py`로 똑같이 반복하면
됩니다.)

**보안 주의**: `scripts/3_fetch_routes.js`와 `scripts/1b_fetch_egen_capacity.js`에
본인의 API 키(카카오 REST API 키 / data.go.kr 인증키)를 채워서 실행한 뒤에는, 그 키가
채워진 채로 깃허브에 올리거나 팀 채널에 공유하지 마세요. 이 저장소에 있는 파일은 키가
각각 플레이스홀더(`<본인의_카카오_REST_API_키를_여기에>`,
`<본인의_data.go.kr_일반인증키(Encoding)를_여기에>`)로 비어 있는 상태입니다.
